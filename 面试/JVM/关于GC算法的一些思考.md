# 关于GC算法的一些思考

### Q1：标记-整理算法和标记-复制算法都涉及到移动存活对象，为什么标记-复制算法效率较高？

标记-复制算法之所以在特定场景下效率更高，主要是因为它简化了操作步骤：

- **指针碰撞**：标记-复制算法将存活对象直接按顺序复制到另一块完全干净的内存区域。这样，分配新内存时只需要移动顶部指针，速度极快。
- **扫描次数更少**：标记-复制算法通常可以在遍历对象的同时完成复制，而标记-整理算法为了不产生内存碎片并保持对象顺序，往往需要对内存进行多次的完整扫描（计算新地址、更新引用、移动对象）。
- **受益于“朝生夕死” **：在JVM的新生代中，绝大多数对象存活率极低（通常低于10%）。这意味着标记-复制只需要移动极少数存活对象，工作量非常小。



### Q2：为什么标记-整理算法不能每移动一个对象就立刻更新它的引用？

如果我们要“搬完立刻更新引用”，逻辑上会遇到一个巨大的**搜索成本**问题。

#### 1. 搬家容易，找“邻居”难

假设你把对象 **C** 从 110 米搬到了 100 米。

- **搬家动作**：只需把 **C** 的内容 copy 过去，这很快。
- **更新引用**：你需要找到**全堆**中所有指向 `110米` 的指针，把它们改成 `100米`。

**核心矛盾：** 对象 **C** 内部知道它引用了谁，但它**不知道谁引用了它**。

为了找到那些引用了 **C** 的对象（比如 **A**、**E** 甚至某个线程栈里的变量），GC 必须遍历**整个内存堆**。

如果你每搬一个对象，都要全堆扫描一遍来更新引用，那这个 GC 可能要跑上一整天。

#### 2. 标记-复制算法的“转账单”策略

标记-复制算法之所以能“立刻更新”，是因为它利用了 **From 空间** 还没被毁掉的特性：

1. **留下遗址**：把 **C** 搬到新家后，在旧址 `110米` 处写上新地址 `100米`。
2. **不主动找人**：GC 不会为了 **C** 去翻遍全堆。
3. **顺便更新**：当 GC 扫描到对象 **A** 时，发现 **A** 引用了 `110米`，它抬头一看旧址上的“转账单”，顺手就把 **A** 指向了 `100米`。

#### 3. 为什么标记-整理（原地搬家）做不到？

回到你的提议：**标记-整理**能不能也这么干？

- **空间冲突**：标记-整理是在原地腾挪。如果你把 **C** 挪到了 **B** 的位置，**B** 的数据就被覆盖了。
- **告示牌被踢馆**：如果你想在 **C** 的旧址留个“转账单”，但这个位置马上就要被后面搬来的 **D** 给占了。
- **结果**：你的“转账单”被覆盖了，后面那些还没被扫描到的引用（比如来自线程栈或还没扫到的对象）就再也找不到 **C** 的新家了。
